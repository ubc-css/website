# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Marketing/landing site for UBC's Cognitive Systems Society (CSS) club. React 19 + TypeScript, built with Vite. Routed with `react-router-dom` (`BrowserRouter`) — currently the homepage (`/`, hero + scroll-revealed folder showcase), an Upcoming Events page (`/events/upcoming`), a Past Events page (`/events/past`), a Merch page (`/merch`), an About page (`/about`), and a placeholder Resources page (`/resources`). New sections *within* a page become new components under `src/components/`; new top-level pages go under `src/pages/<Name>/` and get a `<Route>` in `App.tsx`.

## Commands

```bash
npm run dev       # start Vite dev server with HMR
npm run build     # type-check (tsc -b) then production build via Vite
npm run lint      # eslint .
npm run preview   # preview the production build locally
```

There is no test suite configured in this repo.

## Architecture

- `src/main.tsx` wraps `App` in `<BrowserRouter>` and mounts it into `#root` in `index.html`.
- `src/App.tsx` is just the route table: a `<Route element={<Layout />}>` wrapping `<Route path="/" element={<Home />} />`, `<Route path="/events/upcoming" element={<UpcomingEvents />} />`, `<Route path="/events/past" element={<PastEvents />} />`, `<Route path="/merch" element={<Merch />} />`, `<Route path="/about" element={<About />} />`, and `<Route path="/resources" element={<Resources />} />`. Adding a new page means adding a `src/pages/<Name>/<Name>.tsx` and one more `<Route>` here — no other App.tsx changes needed.
- `src/components/Layout/Layout.tsx` is the persistent shell shared by every route (this is what `App.tsx` used to be, before routing existed): the `site-shell` wrapper (pointer-tracking for a CSS spotlight effect, `Layout.css`) rendering `<Cursor /> <Header /> <Outlet /> <Footer />`. Only the `<Outlet />` content — the current page — changes between routes; Header/Footer/Cursor/the spotlight background are identical on every page. `ScrollCue` is *not* here despite being sitewide-feeling — it scrolls to `#folder-showcase`, which only exists on the homepage, so it lives in `src/pages/Home/Home.tsx` instead.
- `src/pages/Home/Home.tsx` — the homepage's content (`<Hero /> <FolderShowcase /> <ScrollCue />`), rendered inside `Layout`'s `<Outlet />`. Has no CSS of its own; it's pure composition, same as `App.tsx` used to be.
- `src/pages/PastEvents/PastEvents.tsx` + `.css` — search box + a native `<select>` year filter (`'All'` or a specific year — a real `number`, not a display string like `'2025/26'`, so `years` sorts numerically via `.sort((a, b) => b - a)` rather than relying on string sort; `src/components/PastEventCard/formatAcademicYear.ts` derives the `'2025/26'`-style label for display) combined with the search text via AND, over an array of past events, each rendered as an `src/components/PastEventCard/PastEventCard.tsx`.
- `src/components/PastEventCard/PastEventCard.tsx` + `.css` — one past event: name/description on the left, a small hand-rolled photo carousel (prev/next buttons with wraparound, clickable dot indicators, no library) on the right, stacking on mobile. Deliberately reuses `FolderPreview.css`'s `.folder` visual language (same asymmetric `border-radius: 6px 26px 26px 26px`, gradient background, colored tab cycling through the same 4 palette accents) so it reads as "the same kind of folder" as the homepage — but as a plain static two-column card, not `FolderPreview`'s absolutely-positioned scatter/hover system, since this page is for browsing rather than a playful reveal. Fades in on scroll via the existing `src/hooks/useInView.ts` (see below), not a new observer.
- `src/pages/UpcomingEvents/UpcomingEvents.tsx` + `.css` — same search-box-over-a-list shape as Past Events, but the year `<select>` is replaced with a `.calendar-view-button` (`target="_blank"`, linking to the club's real Google Calendar — an `/embed?src=...` URL, meant for an `<iframe>`, but it renders fine as a standalone page too, so it works as a plain link here with no iframe needed) since there's no year dimension to filter upcoming events by. A `.mobile-calendar-view-button` icon-only copy (portaled to `document.body`, next to the mobile hamburger) carries the identical href — both must be updated together if the calendar URL ever changes, there's no shared constant. Placeholder events are sorted soonest-first by a real ISO `date` string (`useMemo` + `.localeCompare`, not just the order they're declared in the array — same "store a real sortable value" reasoning as Past Events' numeric year), rendered via `src/components/UpcomingEventCard/UpcomingEventCard.tsx`.
- `src/components/UpcomingEventCard/UpcomingEventCard.tsx` + `.css` — one upcoming event, deliberately mirrored from `PastEventCard`: a single graphic placeholder (`{ alt, src? }`, same `photo.src ? <img> : <span>` pattern as `FolderPreview`'s photo slots) on the **left** this time, and a body on the **right** built for a call to action rather than browsing — name, a date/time/location meta line (`src/components/UpcomingEventCard/formatEventDate.ts` formats the stored ISO date for display as `"Friday, September 11"` — weekday included since that's what people plan around, year omitted since upcoming events are always only months away. It parses via `new Date(\`${iso}T00:00:00\`)`, i.e. *local* midnight: a bare `new Date("2026-09-11")` parses as UTC and renders as the previous day for anyone behind UTC, which since the weekday was added shows a visibly wrong day name, not just a subtly wrong date — verified in `America/Vancouver` that the bare parse yields "Thursday, September 10" where the local parse correctly yields "Friday, September 11"), description, then two very differently-weighted actions: a filled gradient `.rsvp-button` (same gradient as the site's primary "Become A Member" CTA, so it reads as the button that matters; `target="_blank" rel="noreferrer"` like every other external link on the site, since each event's `rsvpHref` is a real external Luma page and leaving the events list open behind it means nobody loses their place) and a plain underlined `.upcoming-member-link` "Become a member" text link — deliberately not styled as a button, so it never competes with RSVP for attention. Reuses the same `.folder`-style card shell (asymmetric corners, gradient background, cycling colored tab) as `PastEventCard`.
- Both `formatAcademicYear.ts` and `formatEventDate.ts` live as their own module next to the card component that uses them, rather than being exported from the card's own `.tsx` file — a component file exporting anything else trips `react-refresh/only-export-components`.
- `.merch` itself has **no top padding** (`padding: 0 22px clamp(48px, 6vw, 80px)`), unlike a typical section — `.merch-hero` is always its first child and is a colored full-bleed block, so any padding here just showed as a plain-background gap before the color started, reading as a visible seam right under the header. The only gap now is `.site-header`'s own `margin-bottom: 18px`, the same small gap every page already has.
- `src/pages/Merch/Merch.tsx` + `.css` — a hero (`.merch-hero-copy` eyebrow+`<h1>`+lede, then `MerchCarousel`, then a `.merch-section-nav` of plain `#fragment` links to the sections below, same native-smooth-scroll approach as `#folder-showcase`/`ScrollCue`, no JS scroll handler) sized to fill the initial viewport the same way the homepage's `.hero-section` does — `min-height: calc(100svh - 130px)` on `.merch-hero`'s flex column, reusing that exact same header-height offset for consistency. `.merch-hero`'s `gap` (`clamp(18px, 2.2vw, 26px)`) and `MerchCarousel`'s desktop item size (`clamp(280px, min(30vw, 50vh), 520px)`) both count twice toward how far down `.merch-section-nav` sits. The carousel size was originally kept conservative specifically to keep the nav above the fold on common desktop viewport heights — since then, deliberately enlarged past that constraint per an explicit request to push the nav further down the page instead (verified at 1440x900: the nav now sits right at/just past the fold rather than comfortably above it, which is the intended tradeoff now, not a regression). Unlike `.hero-section` (which drops to `min-height: auto` under `max-width: 980px`), the merch hero deliberately keeps filling the viewport on mobile too — explicitly requested, since the carousel is the point of the page's opening screen, so there's no "awkward empty space" argument for shrinking it there the way there is on the homepage. Content is `justify-content: flex-start` rather than centered: the copy block sits near the top, and `MerchCarousel` (naturally sized, not `flex: 1` — see its own CSS for why that was tried and reverted) plus `.merch-hero`'s own `gap` puts a normal, consistent gap between the carousel and the nav rather than the huge invisible one flex-growing the carousel produced. `.merch-hero-copy` mirrors `Hero.tsx`'s `.hero-copy` shape (a small-caps `.merch-hero-eyebrow` kicker with a short gradient line before it, an `<h1>`, a `.merch-hero-lede` subtitle) but reimplemented under its own classes rather than shared, and — unlike `.hero-copy` — with no card/border/background around the group at all; `.merch-hero` itself carries a much subtler two-radial-gradient color wash (low-opacity pink/blue tints) for a bit of depth instead — each gradient has 4 intermediate opacity stops stepping gradually down to `transparent` at 85% (a single middle stop still read as a visible ring; several small steps spread that far out means the glow disappears well before its own edge, with no hard line anywhere), centered around `20%/38%` and `80%/34%` — well down from the box's own top edge (was `18%/15%`/`82%/12%`), since a center that close to the top still left the color fairly saturated exactly where the box meets the header above it, so the box's top edge itself (not the gradient's own falloff) read as a hard line. An outline/card treatment mirroring `.hero-copy`/`.mascot-frame`'s actual border+background+shadow was tried earlier and explicitly reverted — the color wash was the replacement once the hero started feeling too flat. `.merch-hero` is also full-bleed (`width: 100vw` + negative `calc(50% - 50vw)` margins, the same trick `Footer.css` uses, safe for the same reason: `.site-shell` already has `overflow-x: hidden`) with *no* horizontal padding of its own, so the color wash and `MerchCarousel` (a `width: 100%` direct child) span the entire browser window on every screen size rather than stopping at `.merch`'s 1180px content column. `.merch-hero-copy` and `.merch-section-nav` each carry their own `padding-inline: 22px` instead, so the text still clears the screen edges while the carousel doesn't. On desktop the title is sized/tracked to stay on one line (`white-space: nowrap` + a viewport-width-heavy `font-size` clamp — verified no horizontal overflow at 1280px); on mobile it's allowed to wrap (`white-space: normal`) at an even bigger font-size instead of shrinking to fit one line — verified no horizontal overflow at 360px/375px either. `.merch-hero`'s `padding-bottom` is bigger than a typical section's (`clamp(48px, 7vw, 88px)`) so the nav has real breathing room from the hero's own bottom edge. `.merch-section-nav` links are underlined by default (not just on hover, same recipe as `UpcomingEventCard`'s `.upcoming-member-link`) so they read as clickable at a glance. Then a Clothing section, an Accessories section, and a "Like What You See?" purchasing section, each `id`-anchored (`#clothing`/`#accessories`/`#purchasing`) to match the nav. Clothing/Accessories each have a `.merch-section-title-row` (`<h2>` + a sort `<select>`, same `.year-filter`-style pill as Past Events') above their `.merch-grid` (3 columns desktop, 1 on mobile) of `src/components/MerchProductCard/MerchProductCard.tsx`. Each section's sort is independent local state (`clothingSort`/`accessoriesSort`, both `MerchSort` — `'newest' | 'oldest' | 'price-low' | 'price-high'`, defaulting to `'newest'`), applied via a shared `sortMerchItems` helper over a `useMemo`'d copy of that section's array (never mutates the source `clothingItems`/`accessoryItems`). Price sorting re-derives a number from the display string (`parsePrice`, strips everything but digits/`.`) rather than comparing the `"$45"` text directly. A second, independent "Group by Type" filter (`clothingType`/`accessoriesType`, defaulting to the `ALL_TYPES` sentinel — lowercase `'all'`, so it can't collide with a real capitalized `type` value) sits next to the sort dropdown in a `.merch-section-filters` wrapper (needed so `.merch-section-title-row`'s `justify-content: space-between` still only sees two flex children — `<h2>` and this group — instead of spacing three items evenly apart) and narrows the array by `MerchProductCardProps`'s `type` field (applied via `filterMerchItemsByType` *before* `sortMerchItems`, both inside the same `useMemo`) before sorting. `type` is a per-product free-form string, hidden like `year` — never rendered on the card, it exists purely for this filter — and each section's dropdown options (`clothingTypes`/`accessoryTypes`, via `getMerchTypes`) are derived from that section's own array rather than hardcoded, so adding or removing a product automatically updates the available filter options with nothing else to keep in sync. The purchasing section is two `.merch-purchase-option` cards side by side (stacking on mobile): Option 1 pairs explanatory text with a `.merch-order-button` (same gradient as the site's primary "Become A Member" CTA, `href="#"` placeholder until the club has a real external order form) — Option 2 is just informational text, no button, since buying in person needs no link. Product names/descriptions/prices are still explicit placeholder copy (until the club sets real ones), but the photos themselves are the club's real product shots (`src/assets/merch/*.png`, e.g. `zipup-front.png`/`zipup-back.png`, `robbieHoodie-front.png`/`-back.png`, `boboRobbie.png`, `robbieTote.png`) — one card per distinct product, and any product photographed from both sides (a `-front`/`-back` filename pair) supplies both as that card's `images` array rather than getting split into two cards or losing the back view. The 9 individual sticker designs (6 Robbie-expression ones — `bobo`/`love`/`nerd`/`confused`/`shy`/`cryRobbie.png` — plus `cognitivesisyphusSticker.png`, `cogsportalSticker.jpg`, and `robbiexwugSticker.jpg`, added afterward as more real designs turned up) replaced a single earlier "COGS Sticker Pack" placeholder card that had no real per-design photos to show — now each design gets its own card (`type: 'Sticker'`) instead of being lumped into one generic "pack" tile. The original 3 generic placeholder images (`MerchHoodies.png`/`MerchKeychain.png`/`MerchStickers.png`) are no longer used in the product grids, only still in `carouselImages` for the hero's `MerchCarousel` strip (which wasn't part of this photo update) and as the one remaining stand-in for "Robbie Enamel Pin" (`merchKeychain` — there's no real pin photo yet, so it still reuses the keychain's stock photo, same as before).
- `src/components/MerchCarousel/MerchCarousel.tsx` + `.css` — the hero's photo strip, modeled on ubcuxhub.ca's "people behind the process" marquee rather than `PastEventCard`'s click-through carousel: no arrows, no dots, purely automatic. `.merch-carousel` deliberately is **not** `flex: 1` — that was tried (to grow the container to fill the hero's leftover height) but `.merch-carousel-item`'s own size stays capped regardless (`width: clamp(..., 46vh, ...)`), so the growing container just left a big invisible gap between the visibly-capped-size images and the section-nav below. It's sized by its own content instead, with `.merch-hero`'s own `gap` providing normal, consistent spacing to the nav. `overflow: hidden` and an edge `mask-image`/`-webkit-mask-image` fade the strip out at both edges into `.merch-hero`'s color wash instead of clipping hard. `.merch-carousel-item`'s width clamp uses `min(vw, vh)` — not just `vw` — on both desktop (`clamp(280px, min(30vw, 50vh), 520px)`) and its `max-width: 980px` mobile override (`clamp(260px, min(72vw, 44vh), 420px)`), so the photos grow into extra vertical room instead of staying a fixed small size regardless of screen height. The mobile clamp in particular is deliberately bigger relative to its desktop counterpart (72vw vs 30vw) — on mobile the opposite problem from desktop showed up: a small carousel left a lot of *unused* vertical room in the hero, and the nav sat higher than it needed to. Both sizes were later enlarged again past their original values, per an explicit request to make the nav sit lower on the page. The image list is rendered twice back to back in one flex `.merch-carousel-track`; a `requestAnimationFrame` loop (same technique as `Cursor.tsx`'s continuous motion — a plain CSS `@keyframes` version of this was tried first and turned out to silently stall in some browser contexts) writes `translateX` on the track directly each frame, wrapping the offset back by exactly half the track's `scrollWidth` once it passes that point — since the second half is an identical copy of the first, the wrap is invisible and the strip appears to scroll forever. Two speeds, both applied every frame off a single `isHovered` ref flag (not a re-render): the full `speed` (90px/s) normally, dropping to a slower but still-nonzero `hoverSpeed` (22px/s) on `:hover`/`:focus` — deliberately never a full stop. Deliberately does **not** stop for `prefers-reduced-motion` like the rest of the site's automatic motion does — explicitly requested to always keep moving. The whole track is `aria-hidden` (and each image's `alt` is emptied) since it's a decorative repeat of photos that already have real alt text on the product cards below. Each image slot still follows `FolderPreview.photo-slot`'s placeholder pattern (`{ alt, src? }`, dashed box until `src` is set, transparent/borderless via `:has(img)`).
- `src/components/MerchProductCard/MerchProductCard.tsx` + `.css` — one product tile: an `images: MerchProductImage[]` array on top (same placeholder-until-`src`-is-set / `:has(img)` pattern as `UpcomingEventCard`'s graphic for each photo), name/description/price below, plus a `year: number` in `MerchProductCardProps` that's never rendered — it exists purely so `Merch.tsx`'s sort dropdown can order oldest/newest correctly, same "store a real sortable value, not a display string" reasoning as Past Events' numeric year. A single-photo product renders exactly like a plain static image, no controls — only `images.length > 1` (every Clothing item, each with a real `-front`/`-back` photo pair) adds `.merch-product-carousel-arrow` prev/next buttons and `.merch-product-carousel-dot` indicators, the identical hand-rolled carousel recipe `PastEventCard` uses (`useState` index, wraparound prev/next, clickable dots) with `merch-product-` prefixed classnames instead of shared ones. `.merch-product-image img`'s default `object-fit` is `contain` — right for Accessories, whose photos (flat sticker illustrations, a single centered keychain/tote shot) look wrong cropped — but `#clothing .merch-product-image img` overrides it to `cover`: Clothing's real photos have very mixed native aspect ratios (the zip-up hoodie's shots are tall, ~739x964, versus the crewneck's wide ~597x448), and `contain` let each one keep its own size within the square frame, so a tall photo's garment rendered noticeably smaller (letterboxed) than one in a near-square photo; `cover` fills the square edge-to-edge for every Clothing photo instead, cropping whichever axis runs long, so every card's garment reads as roughly the same size. Scoped to `#clothing` specifically (not the shared default) since Accessories doesn't have — and shouldn't get — this treatment. `cover` crops evenly top-and-bottom by default for a portrait photo like the zip-up hoodie's, which cut into the hood near the top of frame — `MerchProductImage` has an optional `objectPosition` (applied as an inline `style` on the `<img>`, since it's a per-photo override rather than a class-level default) for exactly this, and the zip-up's two photos in `Merch.tsx` set it to `'top'` so the crop comes off the hem at the bottom instead. `.merch-product-price` is pinned to the card's bottom-left rather than just trailing the description: `.merch-product-body` takes `flex: 1` so it absorbs the card's leftover height, and the price takes `margin-top: auto` so it eats all of that leftover above itself. Since `.merch-grid` stretches every card in a row to the tallest one's height (grid's default `align-items: stretch`), the prices land on a common baseline across each row instead of stepping up and down with each description's length — verified at a uniform 31px from the card's bottom and left edges on desktop (22.7px on mobile, tracking the card's own `clamp()` padding) across all 18 cards. The price keeps a `padding-top: 4px` rather than a `margin-top`, since the auto margin is doing the positioning; when a description is long enough to fill the body on its own the auto margin collapses to zero and the body's 6px `gap` still keeps the two apart. Both the image frame and the dots row live inside a `.merch-product-carousel` wrapper (a plain flex column with no styling of its own — it adds no extra gap when the dots row doesn't render, so a single-photo card is pixel-identical to before carousel support existed). Reuses `PastEventCard`/`UpcomingEventCard`'s card shell (asymmetric corners, gradient background) but swaps their colored folder *tab* for a `.merch-product-clip` — an inline paperclip SVG (the standard Feather/Lucide paperclip glyph, which is drawn along a 45deg diagonal by default) rotated `-45deg` to stand it upright. It's a sibling of `.merch-product-carousel` (a direct child of the card) and positioned with a `top` negative enough to clear the *card's* own padding and border, not just the image's — so the loop end pokes out above the whole card rectangle sitting behind the photo, not just above the photo inset inside it. Tinted via the same cycling `--merch-accent` variable; reads as a clipped photo/file rather than a folder, matching a product catalog's feel over the events pages' "browsing a folder" feel.
- `src/pages/About/About.tsx` + `.css` — built from a hand-drawn layout sketch, same process as Merch. A hero (a full-width, centered `.about-hero-title` — `<h1>Meet the CSS</h1>` — on its own line, then an `.about-hero-content` row below it pairing a `.about-hero-mission` statement in `.about-hero-copy` on the left with a real framed photo on the right, then an `.about-section-nav` of plain `#fragment` links below — same recipe as Merch's `.merch-section-nav`, no JS scroll handler) sized to fill the initial viewport the same way Merch's hero does, including staying full-height on mobile (Merch's explicit choice, not the homepage hero's "shrink on mobile" default — this page was asked to match Merch specifically). The title used to sit inside `.about-hero-copy` alongside the mission text (both in the left column, image to the right) — moved out to its own full-width line above that row instead, per explicit layout feedback. `.about-hero-mission` was briefly sized as a big italic pull-quote (`clamp(1.9rem, 3.2vw, 2.8rem)`, a narrow `max-width: 21rem`) to visually balance against the full-height photo while it only held a short one-line placeholder — but once real copy (a full 2-sentence paragraph) replaced that placeholder, the same sizing wrapped it to 6+ lines and ~1150px tall, badly overflowing the hero. Reverted to regular lede-scale copy (`clamp(1.05rem, 1.6vw, 1.2rem)`, same scale as `Hero.css`'s `.lede`, `max-width: 34rem` so it wraps at a normal width instead of an artificially narrow one, no italic) — worth remembering that a size tuned for short placeholder text can silently break once real (longer) copy replaces it, so re-check text-driven sizing like this whenever placeholder copy gets swapped for the real thing. Bumped up again afterward once that was confirmed safe — at the smaller size the paragraph left a lot of visibly empty space in the hero. It has since been folded into the hero's height-budget system (see below), so its size is now `clamp(1.05rem, min(1.9vw, var(--hero-avail) * 2.9%), 1.65rem)` rather than a width-only clamp, with its own smaller `max-width: 980px` override (a narrow screen never reaches the vw term, and stacked full-width the desktop size wrapped it into 8-9 lines) and a further short-screen floor below that. A `.about-hero-eyebrow` sits above the title — the same small-caps-kicker-plus-gradient-line recipe as Merch's `.merch-hero-eyebrow`, reimplemented under its own class for the same reason Merch's isn't shared from `Hero.css`. Unlike Merch's version, it only has a leading line (`::before`), not one on each side — an early two-sided draft, combined with a longer first-draft copy ("The Cogs That Keep CSS Turning" / "The Cogs Behind CSS"), wrapped onto 2 lines on narrow screens; the final copy ("The Cogs That Power The Club") stays on one line with the single-sided version. `.about-hero-title`'s size was later synced to Merch's own `.merch-hero h1` scale (`clamp(2.2rem, 9vw, 6.5rem)`, up from an earlier, smaller `clamp(2.6rem, 6vw, 4.6rem)`) — a further step toward the two heroes actually matching, not just resembling each other. The right-hand hero graphic (`.about-hero-image`) deliberately reuses `Hero.css`'s `.mascot-frame` visual language (two-tone radial gradient wash, faint grid overlay masked to a center vignette, border + shadow) rather than the site's usual dashed-box photo placeholder — it's a single static framed graphic like the mascot, not a small tile in a grid/strip, so it earns the more polished treatment. It originally held a placeholder box; now holds a real photo, `src/assets/about/execsAndFaculty.jpg` (compressed the same way as every other real photo on the site — `sharp`, resized to a 1400px long edge, JPEG quality 80/mozjpeg — down from a 5.65MB/5184×3888 original to 135KB/1400×1050), preloaded via `preload()` + a detached `Image().decode()` the same way Merch's carousel photos are, since it's above-the-fold. `.about-hero-image`'s `aspect-ratio` was changed from an earlier placeholder-era `4 / 5` to `4 / 3` to exactly match this photo's real native ratio — the photo is a wide group shot with people spread edge-to-edge, so any `object-fit: cover` crop (needed regardless, since the box's width is fluid while the photo's isn't) would have cut people off at the sides under the old, taller placeholder ratio. Matching the ratio means `cover` never actually needs to crop anything in practice. The mobile breakpoint's now-redundant `aspect-ratio: 4 / 3` override was removed since the base rule already matches. Same lesson as the mission-text overflow above: a container's shape/sizing tuned for a placeholder needs re-checking once real content replaces it, not just carried over as-is. **This hero is sized against a height budget, and that is the whole design.** The requirement it's built to satisfy: the eyebrow, title, mission/photo row and nav all stay vertically proportionate at any size, the nav sits centered between the bottom of the photo row and the bottom of the window, and the nav is *never* below the fold on first load on any device. `.about-hero-inner` renders eyebrow → title → `.about-hero-content` → `.about-hero-nav-spacer` (which wraps the `<nav>`), and declares two custom properties every vertical measurement below is derived from:

- `--hero-top-offset` — the real distance from the top of the window to the top of the hero: `.site-header`'s height plus its 18px margin, i.e. **124px desktop / 110px mobile** (the header shrinks at `980px`). Measured, not guessed. The rest of the site approximates this as a flat `calc(100svh - 130px)`, which overshoots by 6px desktop and 20px mobile; that slop is harmless on Merch/Home (nothing there is positioned against the hero's *bottom*) but here it left the hero ending 20px short of the bottom of the window and threw the nav's centering off by exactly that. Keep in sync with `Header.css`.
- `--hero-h` = `100svh - var(--hero-top-offset)` (the hero's height, and its `min-height`), and `--hero-avail` = `--hero-h - 64px`, which further subtracts the two things that *can't* scale — the eyebrow's line box and the nav's. The title, photo and gaps are then sized as shares of `--hero-avail`: `0.15`, `0.74` (its *width*, so ~0.55 of the budget as height via the 4/3 ratio) and `0.035` respectively.

`svh` throughout, never `vh`/`dvh` — it's the *small* viewport height, the worst case with mobile browser chrome expanded, which is exactly the state a page is in when it first loads.

The reason this is all keyed to height: **a width-only clamp keeps growing the title/photo/gaps on a wide but short window until the stack no longer fits one screen.** Every earlier version of this hero sized those from `vw` alone (or from raw `svh`, which is nearly as bad — the fixed header eats 14% of a 900px-tall window but 33% of a 390px one, so a coefficient tuned on the former leaves no room on the latter). Two bugs of exactly that shape were fixed here: the `980px` stacking breakpoint was width-only, so it handed the *taller* stacked layout to landscape phones — the one kind of screen with the least height to spare — and is now gated on `(max-aspect-ratio: 1/1)` as well; and the photo was sized by `fr` units off the container's width through a long series of hand-tuned ratios (1.1/0.85 → 1/1.05 → 0.75/1.35 → 0.7/1.4, re-tuned every time anything above it changed size), and is now `grid-template-columns: minmax(0, 1fr) auto` with the photo sizing itself and the text taking the remainder. Sizing the photo via `width` rather than `max-height` is deliberate: a height cap on a `width: 100%` box would distort the frame and make `object-fit: cover` start cropping people out of the edge-to-edge group shot again.

`.about-hero-nav-spacer` (`flex: 1`) consumes everything left after the content row and centers the nav in it, and `.about-hero-inner`'s `padding-bottom` is set to exactly one `--hero-gap` — the same value as the gap above the spacer. That equality is load-bearing, not cosmetic: the nav's space-above is `gap + half the spacer` and its space-below is `half the spacer + padding-bottom`, so the two are equal, and the links are *exactly* centered between the photo row and the bottom of the window, only when those two match. This replaced a fixed `margin-top` on the nav (nudged 24px then 56px by hand) that only looked centered at the one screen size it was picked on.

One thing the height budget genuinely can't express: a wrapped paragraph's height is a function of its *width* (narrower column → more lines) while the budget it must fit is a function of height, and no CSS expression relates the two. So on a small phone the mission copy wraps to ~9 lines and eats the budget after every other clamp is already at its floor — and those floors exist for legibility. The stacked-phone rules also deliberately diverge from desktop in four ways, all scoped inside the `(max-aspect-ratio: 1/1)` query so desktop and landscape are untouched: the photo takes the full column width (`min(100%, --hero-avail * 0.95, 460px)`) and is `justify-self: center` — without that it sits at the column's left edge, which is what made it read as a small box floating in the left half of the screen; `.about-hero-content` gets its own `margin-top` for a wider title-to-mission gap (done here rather than by widening `--hero-gap`, which also sets eyebrow-to-title and content-to-nav spacing); `.about-hero-inner` gets a larger `padding-top` so the hero sits lower under the header; and the mission text runs a notch larger. The flat `460px` term is what keeps the full-width rule a *phone* rule — a 768px-wide tablet still stacks, and there 100% of the column is a 724px-wide photo (543px tall) that overran the budget on its own and put the nav below the fold. **The mobile photo/spacing tiers, and the trap in them.** The stacked hero has three height bands (`>780px`, `621–780px`, `≤620px`), each giving the photo a different cap, plus its own padding/mission trims. Two lessons are baked in. First: **a phone's usable viewport is far shorter than its spec sheet** — a 430pt-wide phone in an in-app browser reports about `430×698`, because the surrounding chrome eats ~150px. A `max-height: 700px` breakpoint intended for tiny phones therefore swallowed ordinary modern ones, handing a 430px-wide device the photo cap tuned for a 320px screen: 55% width with an 84px band of dead space above the links. Assume any `max-height` here catches bigger devices than it looks like it should. Second: within a band the photo cap is **affine in `--hero-avail`** (`calc(var(--hero-avail) * 1.15 - 245px)`), not a flat multiple of it — the fixed costs (title, eyebrow, nav, gaps) don't shrink with the viewport, so they take proportionally more of a 620px screen than a 780px one, and any single coefficient that fits one end of a band starves the other. The eyebrow's tightening is width-gated (`max-width: 400px`) rather than height-gated, because whether it wraps is purely about width: measured, its text run is 292px plus a 44px rule and 12px gap, so it needs a 392px viewport for one line — re-measure that if the eyebrow copy ever changes. Hence one deliberate short-screen tier (`max-width: 980px and max-height: 620px`) that lowers just the mission's floor and tightens the content gap, plus a stacked-and-short tier that scales back the phone enlargements (smaller photo cap, `padding-top` and content `margin-top`) — the smallest phones can't carry them, and applied together they put the nav 65px below the fold at 320×568. The visible cost is that a genuinely short phone gets a smaller photo (~53% of viewport) than a tall one (~88–90%); on a 568px-tall screen there isn't room for both. That tier is what takes 320×568 from the nav sitting 53px below the fold to comfortably above it.

Verified by DOM measurement — nav fully on screen and gap-above exactly equal to gap-below (0px error) — at **1920×1080, 1440×900, 1440×700, 1366×620, 1024×768, 980×700, 768×1024, 390×844, 375×812, 360×640, 320×568, and landscape 844×390, 667×375, 568×320**. Re-run that sweep after any change to the hero's sizing; the short/narrow and landscape-phone cases are where it breaks first, and 320×568 and 568×320 are the tightest (~15–24px of slack either side of the nav). Bottom row is just the logo (bottom-left, no brand text) and a "Contact us!" label + mailto/Instagram/LinkedIn/Linktree/Discord icon links (bottom-right), all five in the identical shared circular `.footer-contact a` button (white-tinted background, black by default, `var(--color-gray-blue)` on hover). Mail/Instagram/LinkedIn are plain black hand-drawn line-art stand-ins, not reproductions of those brands' real logos. Linktree and Discord instead render their *actual* logo paths (sourced verbatim from `simple-icons/simple-icons`'s `icons/linktree.svg` / `icons/discord.svg`) with `fill="currentColor"` in place of each brand's own color — real shapes, but recolored/reshaped to match the rest of the row rather than getting their own brand-colored squircle (that per-brand-colored treatment was tried and reverted — it read as inconsistent with the other three). The Discord link (`href="https://discord.com/invite/ndq7epCG4F"`) is the club's real invite. The email and social URLs are real (found via web search, not guessed) but weren't confirmed by the club — verify before relying on them. On mobile the logo needs to visually reorder above everything (columns/CTA, then contact), even though it's nested inside `.footer-bottom` alongside the contact icons in the markup (kept nested so desktop's brand+contact same-row layout needs no separate markup) — the `max-width: 980px` query gives `.site-footer` a flex column and sets `.footer-bottom { display: contents; }`, which "unwraps" it so `.footer-brand` and `.footer-contact` become independently-orderable flex children of `.site-footer` right alongside `.footer-top`, each with its own `order`.

## Styling

- No CSS modules/Tailwind/styled-components — plain CSS, one stylesheet per component, imported by that component (`import './Header.css'` in `Header.tsx`, etc). `Layout.css` only holds the root `site-shell` background/grid-overlay layers. Base/reset styles and site-wide color variables are global, in `src/index.css`.
- Color palette and fonts are defined as CSS custom properties on `:root` in `src/index.css` (`--color-*` variables; fonts are Fraunces for headings, Manrope for body, loaded via Google Fonts `@import`). Reuse these variables rather than hardcoding colors.
- Responsive behavior is handled with plain `@media` queries colocated in each component's own CSS file (main breakpoint at `980px`, plus `hover`/`pointer` and `prefers-reduced-motion` queries) — there is no CSS framework.
- `src/styles/future-sections.css` holds styling for nav items that don't have a built page section yet (Events/Merch/Resources/About — things like `.join-strip`, `.mini-stats`, `.info-grid`, `.stream-list`). **This file is intentionally not imported anywhere.** When you build one of those sections, pull the relevant rules out into that new component's own CSS file rather than importing this file wholesale.

## TypeScript config notes

- `noUnusedLocals` / `noUnusedParameters` / `noFallthroughCasesInSwitch` are enabled — unused variables/params will fail `tsc -b` (and thus `npm run build`).
- `verbatimModuleSyntax` is on — type-only imports must use `import type { ... }`.
