# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Marketing/landing site for UBC's Cognitive Systems Society (CSS) club. React 19 + TypeScript, built with Vite. Routed with `react-router-dom` (`BrowserRouter`) — currently the homepage (`/`, hero + scroll-revealed folder showcase), an Upcoming Events page (`/events/upcoming`), a Past Events page (`/events/past`), and a Merch page (`/merch`). New sections *within* a page become new components under `src/components/`; new top-level pages go under `src/pages/<Name>/` and get a `<Route>` in `App.tsx`.

## Commands

```bash
npm run dev       # start Vite dev server with HMR
npm run build     # type-check (tsc -b) then production build via Vite
npm run lint      # eslint .
npm run preview   # preview the production build locally
```

There is no test suite configured in this repo.

## Architecture

- `src/main.tsx` wraps `App` in `<BrowserRouter>` and mounts it into `#root` in `index.html`.
- `src/App.tsx` is just the route table: a `<Route element={<Layout />}>` wrapping `<Route path="/" element={<Home />} />`, `<Route path="/events/upcoming" element={<UpcomingEvents />} />`, `<Route path="/events/past" element={<PastEvents />} />`, and `<Route path="/merch" element={<Merch />} />`. Adding a new page means adding a `src/pages/<Name>/<Name>.tsx` and one more `<Route>` here — no other App.tsx changes needed.
- `src/components/Layout/Layout.tsx` is the persistent shell shared by every route (this is what `App.tsx` used to be, before routing existed): the `site-shell` wrapper (pointer-tracking for a CSS spotlight effect, `Layout.css`) rendering `<Cursor /> <Header /> <Outlet /> <Footer />`. Only the `<Outlet />` content — the current page — changes between routes; Header/Footer/Cursor/the spotlight background are identical on every page. `ScrollCue` is *not* here despite being sitewide-feeling — it scrolls to `#folder-showcase`, which only exists on the homepage, so it lives in `src/pages/Home/Home.tsx` instead.
- `src/pages/Home/Home.tsx` — the homepage's content (`<Hero /> <FolderShowcase /> <ScrollCue />`), rendered inside `Layout`'s `<Outlet />`. Has no CSS of its own; it's pure composition, same as `App.tsx` used to be.
- `src/pages/PastEvents/PastEvents.tsx` + `.css` — search box + a native `<select>` year filter (`'All'` or a specific year — a real `number`, not a display string like `'2025/26'`, so `years` sorts numerically via `.sort((a, b) => b - a)` rather than relying on string sort; `src/components/PastEventCard/formatAcademicYear.ts` derives the `'2025/26'`-style label for display) combined with the search text via AND, over an array of past events, each rendered as an `src/components/PastEventCard/EventCard.tsx` (component folder is `PastEventCard`; the file/component name inside stayed `EventCard`).
- `src/components/PastEventCard/EventCard.tsx` + `.css` — one past event: name/description on the left, a small hand-rolled photo carousel (prev/next buttons with wraparound, clickable dot indicators, no library) on the right, stacking on mobile. Deliberately reuses `FolderPreview.css`'s `.folder` visual language (same asymmetric `border-radius: 6px 26px 26px 26px`, gradient background, colored tab cycling through the same 4 palette accents) so it reads as "the same kind of folder" as the homepage — but as a plain static two-column card, not `FolderPreview`'s absolutely-positioned scatter/hover system, since this page is for browsing rather than a playful reveal. Fades in on scroll via the existing `src/hooks/useInView.ts` (see below), not a new observer.
- `src/pages/UpcomingEvents/UpcomingEvents.tsx` + `.css` — same search-box-over-a-list shape as Past Events, but the year `<select>` is replaced with a `.calendar-view-button` (a placeholder `href="#"`, `target="_blank"` link — swap in the club's real external calendar URL once one exists) since there's no year dimension to filter upcoming events by. Placeholder events are sorted soonest-first by a real ISO `date` string (`useMemo` + `.localeCompare`, not just the order they're declared in the array — same "store a real sortable value" reasoning as Past Events' numeric year), rendered via `src/components/UpcomingEventCard/UpcomingEventCard.tsx`.
- `src/components/UpcomingEventCard/UpcomingEventCard.tsx` + `.css` — one upcoming event, deliberately mirrored from `EventCard`: a single graphic placeholder (`{ alt, src? }`, same `photo.src ? <img> : <span>` pattern as `FolderPreview`'s photo slots) on the **left** this time, and a body on the **right** built for a call to action rather than browsing — name, a date/time/location meta line (`src/components/UpcomingEventCard/formatEventDate.ts` formats the stored ISO date for display), description, then two very differently-weighted actions: a filled gradient `.rsvp-button` (same gradient as the site's primary "Become A Member" CTA, so it reads as the button that matters) and a plain underlined `.upcoming-member-link` "Become a member" text link — deliberately not styled as a button, so it never competes with RSVP for attention. Reuses the same `.folder`-style card shell (asymmetric corners, gradient background, cycling colored tab) as `EventCard`.
- Both `formatAcademicYear.ts` and `formatEventDate.ts` live as their own module next to the card component that uses them, rather than being exported from the card's own `.tsx` file — a component file exporting anything else trips `react-refresh/only-export-components`.
- `src/pages/Merch/Merch.tsx` + `.css` — a hero (`<h1>` + `MerchCarousel` + a `.merch-section-nav` of plain `#fragment` links to the sections below, same native-smooth-scroll approach as `#folder-showcase`/`ScrollCue`, no JS scroll handler) sized to fill the initial viewport the same way the homepage's `.hero-section` does — `min-height: calc(100svh - 130px)` on `.merch-hero`'s flex column, reusing that exact same header-height offset for consistency. Unlike `.hero-section` (which drops to `min-height: auto` under `max-width: 980px`), the merch hero deliberately keeps filling the viewport on mobile too — explicitly requested, since the carousel is the point of the page's opening screen, so there's no "awkward empty space" argument for shrinking it there the way there is on the homepage. Content is `justify-content: flex-start` rather than centered: the `<h1>` sits near the top and `MerchCarousel` takes `flex: 1` to grow and fill the rest of the hero's height, so *it* reads as the actual hero image rather than a strip under the title. On desktop the title is sized/tracked to stay on one line (`white-space: nowrap` + a viewport-width-heavy `font-size` clamp — verified no horizontal overflow at 1280px); on mobile it's allowed to wrap (`white-space: normal`) at an even bigger font-size instead of shrinking to fit one line — verified no horizontal overflow at 360px/375px either. Neither the title nor the carousel has a card/border around it — an outline treatment mirroring `.hero-copy`/`.mascot-frame` was tried and explicitly reverted. `.merch-section-nav` links are underlined by default (not just on hover, same recipe as `UpcomingEventCard`'s `.upcoming-member-link`) so they read as clickable at a glance. Then a Clothing section, an Accessories section, and a "Like What You See?" purchasing section, each `id`-anchored (`#clothing`/`#accessories`/`#purchasing`) to match the nav. Clothing/Accessories each have a `.merch-section-title-row` (`<h2>` + a sort `<select>`, same `.year-filter`-style pill as Past Events') above their `.merch-grid` (3 columns desktop, 1 on mobile) of `src/components/MerchProductCard/MerchProductCard.tsx`. Each section's sort is independent local state (`clothingSort`/`accessoriesSort`, both `MerchSort` — `'newest' | 'oldest' | 'price-low' | 'price-high'`, defaulting to `'newest'`), applied via a shared `sortMerchItems` helper over a `useMemo`'d copy of that section's array (never mutates the source `clothingItems`/`accessoryItems`). Price sorting re-derives a number from the display string (`parsePrice`, strips everything but digits/`.`) rather than comparing the `"$45"` text directly. The purchasing section is two `.merch-purchase-option` cards side by side (stacking on mobile): Option 1 pairs explanatory text with a `.merch-order-button` (same gradient as the site's primary "Become A Member" CTA, `href="#"` placeholder until the club has a real external order form) — Option 2 is just informational text, no button, since buying in person needs no link. All product data (names/descriptions/prices) is explicit placeholder copy, and photos are the same 3 real merch images already used in `FolderShowcase.tsx` (`MerchHoodies.png`/`MerchKeychain.png`/`MerchStickers.png`), reused across the carousel and both grids — same "reuse the few real photos we have" approach as Past Events' placeholder cards.
- `src/components/MerchCarousel/MerchCarousel.tsx` + `.css` — the hero's photo strip, modeled on ubcuxhub.ca's "people behind the process" marquee rather than `EventCard`'s click-through carousel: no arrows, no dots, purely automatic. `.merch-carousel` is `flex: 1` (so it grows to fill the hero's available height — see `Merch.css` above), `overflow: hidden`, and carries an edge `mask-image`/`-webkit-mask-image` that fades the strip out at both edges into the page background instead of clipping hard. `.merch-carousel-item`'s width clamp uses `min(26vw, 46vh)` — not just `vw` — so the photos actually grow into that extra vertical room instead of staying a fixed small size in the middle of a tall strip. The image list is rendered twice back to back in one flex `.merch-carousel-track`; a `requestAnimationFrame` loop (same technique as `Cursor.tsx`'s continuous motion — a plain CSS `@keyframes` version of this was tried first and turned out to silently stall in some browser contexts) writes `translateX` on the track directly each frame, wrapping the offset back by exactly half the track's `scrollWidth` once it passes that point — since the second half is an identical copy of the first, the wrap is invisible and the strip appears to scroll forever. Two speeds, both applied every frame off a single `isHovered` ref flag (not a re-render): the full `speed` (90px/s) normally, dropping to a slower but still-nonzero `hoverSpeed` (22px/s) on `:hover`/`:focus` — deliberately never a full stop. Deliberately does **not** stop for `prefers-reduced-motion` like the rest of the site's automatic motion does — explicitly requested to always keep moving. The whole track is `aria-hidden` (and each image's `alt` is emptied) since it's a decorative repeat of photos that already have real alt text on the product cards below. Each image slot still follows `FolderPreview.photo-slot`'s placeholder pattern (`{ alt, src? }`, dashed box until `src` is set, transparent/borderless via `:has(img)`).
- `src/components/MerchProductCard/MerchProductCard.tsx` + `.css` — one product tile: image on top (same placeholder-until-`src`-is-set / `:has(img)` pattern as `UpcomingEventCard`'s graphic), name/description/price below, plus a `year: number` in `MerchProductCardProps` that's never rendered — it exists purely so `Merch.tsx`'s sort dropdown can order oldest/newest correctly, same "store a real sortable value, not a display string" reasoning as Past Events' numeric year. Reuses `EventCard`/`UpcomingEventCard`'s card shell (asymmetric corners, gradient background) but swaps their colored folder *tab* for a `.merch-product-clip` — an inline paperclip SVG (the standard Feather/Lucide paperclip glyph, which is drawn along a 45deg diagonal by default) rotated `-45deg` to stand it upright. It's a sibling of `.merch-product-image` (a direct child of the card, not nested inside the image box) and positioned with a `top` negative enough to clear the *card's* own padding and border, not just the image's — so the loop end pokes out above the whole card rectangle sitting behind the photo, not just above the photo inset inside it. `.merch-product-image` keeps a normal `overflow: hidden` since the clip no longer lives inside it. Tinted via the same cycling `--merch-accent` variable; reads as a clipped photo/file rather than a folder, matching a product catalog's feel over the events pages' "browsing a folder" feel.
- Internal navigation to `/events/upcoming`, `/events/past`, and `/merch` (in `Header.tsx`'s `NavDropdown` items and `Footer.tsx`'s mirrored `footerColumns`) deliberately uses a plain `<a href="...">`, not `react-router-dom`'s `<Link>` — correct either way for a small site, and a plain `<a>` avoids threading `Link` through `NavDropdown`/`MobileNav`/`Footer`'s generic `{label, href}` rendering for marginal benefit (the only cost is a full page reload instead of a client-side transition). If more internal routes get added and that reload starts being noticeable, that's the point to introduce `Link` there.
- Each component lives in its own folder under `src/components/<Name>/` with its markup and stylesheet together (`<Name>.tsx` + `<Name>.css`, imported by the component itself). New page sections should follow the same pattern: a new `src/components/<Section>/` folder composed into `App.tsx`, using the existing kebab-case BEM-ish class naming style (`hero-stage`, `hero-copy`, `mascot-frame`, etc). This encapsulation is convention, not enforced — CSS has no real scoping, so a bare tag selector in any component's stylesheet applies everywhere. `Hero.css` had exactly this bug (a bare `h1 { max-width: 12ch; ... }` meant for the homepage's own title, silently constraining every other page's `<h1>` too) until it was caught while giving Merch's title a bigger font — now scoped to `.hero-copy h1`. Double-check for this pattern (an unscoped element selector, not `.some-class`) before assuming a heading/paragraph/etc. on a new page is only affected by that page's own stylesheet.
- `src/components/Header/Header.tsx` owns the `navContent` JSX (nav links + dropdowns + CTA) as one fragment rendered twice: once inside `<nav className="site-nav desktop-only">`, once passed as children to `<MobileNav>`. When editing nav links/dropdowns, edit `navContent` once — both desktop and mobile pick it up.
- `src/components/NavDropdown/NavDropdown.tsx` — reusable hover/click dropdown for nav items (`label` + `items: {label, href}[]` props). On touch devices (`hover: hover` media query fails) it falls back to click-to-toggle instead of CSS hover. Used by both `Header` (desktop) and `MobileNav` (mobile), so `NavDropdown.css` has both a base ruleset and mobile-specific overrides live in `MobileNav.css` (scoped under `.mobile-nav-links`).
- `src/components/MobileNav/MobileNav.tsx` — hamburger button + slide-out panel, rendered via `createPortal` directly into `document.body` (so it isn't affected by header stacking/overflow). Toggles `document.body.style.overflow` while open to lock background scroll.
- `src/components/Cursor/Cursor.tsx` — custom animated cursor (dot + trailing ring) driven by `requestAnimationFrame`, attached via `window` pointer listeners. Self-disables when `matchMedia('(hover: hover) and (pointer: fine)')` is false (touch devices). `Cursor.css` also carries the global `* { cursor: none }` override (and per-element opt-outs) that hides the native cursor everywhere hover is supported — that's a consequence of this feature, not dead code.
- Desktop vs. mobile UI is switched with the `desktop-only` / `mobile-only` CSS classes (defined in `Header.css`), not JS breakpoint checks, except where `matchMedia` is needed to change behavior (cursor, dropdown hover support).
- `Layout.tsx` tracks pointer position on the root `<main>` via `onPointerMove`, writing `--pointer-x` / `--pointer-y` CSS custom properties onto the element for use in CSS (e.g. gradient/spotlight effects in `Layout.css`).
- `src/hooks/useInView.ts` — reusable `IntersectionObserver` hook (`{ ref, isInView }`, reveal-once, threshold configurable) for scroll-triggered entrance animations. `src/components/FolderPreview/FolderPreview.tsx` is the reference usage: it toggles an `is-visible` class from `isInView` and does all the actual animation in CSS transitions. Reuse this hook rather than writing a new observer for the next scroll-reveal section.
- `src/components/FolderPreview/FolderPreview.tsx` + `FolderShowcase.tsx` — the folder-shaped previews below the hero. `FolderShowcase.tsx` owns the data (title/description/href/photos per folder); `FolderPreview.tsx` is the presentational, data-driven single folder. The folder and its 3 photos are absolutely positioned in one shared `.folder-stage` so the photos can start tucked exactly behind the (higher z-index) folder and travel out from underneath it. Each folder's `align: 'left' | 'right'` prop sets a `--dir` CSS custom property that flips both which edge the folder anchors to and the sign of the photos' scatter transform — that's how left/right mirroring is done without duplicating the scatter math. Photos are placeholders (`{ alt }`) until a real image is wanted: add `src` to that photo's data entry in `FolderShowcase.tsx` and it renders an `<img>` instead of the placeholder box, no other changes needed.
- The photo reveal trigger branches on *input capability*, not just viewport width: `(hover: hover) and (pointer: fine)` gets the desktop hover-triggered reveal (plus the pulsing "Hover to explore" `.hover-hint` badge, hidden everywhere else); anything without real hover — phones (`max-width: 980px`) or a desktop-sized touchscreen (`min-width: 981px) and (hover: none)`) — falls back to the same `useInView`-driven scroll reveal, just with different fall directions. `prefers-reduced-motion: reduce` disables all of it by default and then explicitly re-enables the photo transition only for the hover-capable case, since that one is a deliberate user-initiated interaction rather than automatic motion.
- `<section className="folder-showcase" id="folder-showcase">` (in `FolderShowcase.tsx`) is the shared scroll target for "jump to the sections below the hero": both `src/components/ScrollCue/ScrollCue.tsx` (the bouncing bottom-center arrow, shown only while `window.scrollY < 40`, tracked via a plain `scroll` listener rather than `useInView` since it needs continuous position, not a one-shot reveal) and the hero's "Learn what CSS does" link are just plain `<a href="#folder-showcase">`s — the smooth animation is native `scroll-behavior: smooth` on `html` in `index.css`, gated under `@media (prefers-reduced-motion: no-preference)`. No JS scroll handler; a custom `requestAnimationFrame`-eased version was tried and deliberately reverted in favor of the native behavior.
- `src/components/Footer/Footer.tsx` — page footer, deliberately styled *unlike* `.site-header`: a traditional full-bleed bar in `var(--color-dark-plum)` rather than the site's usual centered rounded "card", so it reads as a distinct closing section. `Footer.css` breaks `.site-footer` out of `.site-shell`'s centered padding with the `width: 100vw; margin-left/right: calc(50% - 50vw)` full-bleed trick (safe here specifically because `.site-shell` already has `overflow-x: hidden`), then cancels `.site-shell`'s own bottom padding (`22px` desktop / `14px` mobile — must stay in sync with `Layout.css`) via a matching negative `margin-bottom` + compensating `padding-bottom`, so the dark background reaches the true edges of the page with no gap. Because the background is dark, every descendant color is overridden from the site's default dark-text-on-light to light-on-dark, and the (black-on-transparent) logo image gets `filter: brightness(0) invert(1)` to force it white — don't reuse `.brand-logo`'s styling here, the dark background needs this override. `footerColumns` in `Footer.tsx` is a small sitemap that intentionally mirrors `Header.tsx`'s `NavDropdown` data (same labels/hrefs for Events/Merch/Resources/About) — if the nav dropdowns change, update this array too, there's no shared source of truth between them. Top row is the sitemap columns (left) plus a `.footer-cta-block` (right): a `.footer-cta` "Become a Member" button + a `href="#"` "back to top" link stacked under it (native `#` anchor behavior + the global smooth-scroll from `index.css`, no JS). Bottom row is just the logo (bottom-left, no brand text) and a "Contact us!" label + mailto/Instagram/LinkedIn icon links (bottom-right) via inline SVGs (no icon asset files/libraries). The email and social URLs are real (found via web search, not guessed) but weren't confirmed by the club — verify before relying on them. On mobile the logo needs to visually reorder above everything (columns/CTA, then contact), even though it's nested inside `.footer-bottom` alongside the contact icons in the markup (kept nested so desktop's brand+contact same-row layout needs no separate markup) — the `max-width: 980px` query gives `.site-footer` a flex column and sets `.footer-bottom { display: contents; }`, which "unwraps" it so `.footer-brand` and `.footer-contact` become independently-orderable flex children of `.site-footer` right alongside `.footer-top`, each with its own `order`.

## Styling

- No CSS modules/Tailwind/styled-components — plain CSS, one stylesheet per component, imported by that component (`import './Header.css'` in `Header.tsx`, etc). `Layout.css` only holds the root `site-shell` background/grid-overlay layers. Base/reset styles and site-wide color variables are global, in `src/index.css`.
- Color palette and fonts are defined as CSS custom properties on `:root` in `src/index.css` (`--color-*` variables; fonts are Fraunces for headings, Manrope for body, loaded via Google Fonts `@import`). Reuse these variables rather than hardcoding colors.
- Responsive behavior is handled with plain `@media` queries colocated in each component's own CSS file (main breakpoint at `980px`, plus `hover`/`pointer` and `prefers-reduced-motion` queries) — there is no CSS framework.
- `src/styles/future-sections.css` holds styling for nav items that don't have a built page section yet (Events/Merch/Resources/About — things like `.join-strip`, `.mini-stats`, `.info-grid`, `.stream-list`). **This file is intentionally not imported anywhere.** When you build one of those sections, pull the relevant rules out into that new component's own CSS file rather than importing this file wholesale.

## TypeScript config notes

- `noUnusedLocals` / `noUnusedParameters` / `noFallthroughCasesInSwitch` are enabled — unused variables/params will fail `tsc -b` (and thus `npm run build`).
- `verbatimModuleSyntax` is on — type-only imports must use `import type { ... }`.
