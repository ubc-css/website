# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Marketing/landing site for UBC's Cognitive Systems Society (CSS) club. React 19 + TypeScript, built with Vite. Routed with `react-router-dom` (`BrowserRouter`) — currently the homepage (`/`, hero + scroll-revealed folder showcase) and a Past Events page (`/events/past`). New sections *within* a page become new components under `src/components/`; new top-level pages go under `src/pages/<Name>/` and get a `<Route>` in `App.tsx`.

## Commands

```bash
npm run dev       # start Vite dev server with HMR
npm run build     # type-check (tsc -b) then production build via Vite
npm run lint      # eslint .
npm run preview   # preview the production build locally
```

There is no test suite configured in this repo.

## Architecture

- `src/main.tsx` wraps `App` in `<BrowserRouter>` and mounts it into `#root` in `index.html`.
- `src/App.tsx` is just the route table: a `<Route element={<Layout />}>` wrapping `<Route path="/" element={<Home />} />` and `<Route path="/events/past" element={<PastEvents />} />`. Adding a new page means adding a `src/pages/<Name>/<Name>.tsx` and one more `<Route>` here — no other App.tsx changes needed.
- `src/components/Layout/Layout.tsx` is the persistent shell shared by every route (this is what `App.tsx` used to be, before routing existed): the `site-shell` wrapper (pointer-tracking for a CSS spotlight effect, `Layout.css`) rendering `<Cursor /> <Header /> <Outlet /> <Footer />`. Only the `<Outlet />` content — the current page — changes between routes; Header/Footer/Cursor/the spotlight background are identical on every page. `ScrollCue` is *not* here despite being sitewide-feeling — it scrolls to `#folder-showcase`, which only exists on the homepage, so it lives in `src/pages/Home/Home.tsx` instead.
- `src/pages/Home/Home.tsx` — the homepage's content (`<Hero /> <FolderShowcase /> <ScrollCue />`), rendered inside `Layout`'s `<Outlet />`. Has no CSS of its own; it's pure composition, same as `App.tsx` used to be.
- `src/pages/PastEvents/PastEvents.tsx` + `.css` — search box + a native `<select>` year filter (`'All'` or a specific year, combined with the search text via AND) over a placeholder array of past events, each rendered as an `src/components/EventCard/EventCard.tsx`. The event data and photos are all placeholders (the three real, already-compressed photos in `src/assets/events/` are just cycled across cards) until the club has real past-event content to swap in.
- `src/components/EventCard/EventCard.tsx` + `.css` — one past event: name/description on the left, a small hand-rolled photo carousel (prev/next buttons with wraparound, clickable dot indicators, no library) on the right, stacking on mobile. Deliberately reuses `FolderPreview.css`'s `.folder` visual language (same asymmetric `border-radius: 6px 26px 26px 26px`, gradient background, colored tab cycling through the same 4 palette accents) so it reads as "the same kind of folder" as the homepage — but as a plain static two-column card, not `FolderPreview`'s absolutely-positioned scatter/hover system, since this page is for browsing rather than a playful reveal. Fades in on scroll via the existing `src/hooks/useInView.ts` (see below), not a new observer.
- Internal navigation to `/events/past` (in `Header.tsx`'s `NavDropdown` items and `Footer.tsx`'s mirrored `footerColumns`) deliberately uses a plain `<a href="/events/past">`, not `react-router-dom`'s `<Link>` — correct either way for a 2-page site, and a plain `<a>` avoids threading `Link` through `NavDropdown`/`MobileNav`/`Footer`'s generic `{label, href}` rendering for marginal benefit (the only cost is a full page reload instead of a client-side transition). If more internal routes get added and that reload starts being noticeable, that's the point to introduce `Link` there.
- Each component lives in its own folder under `src/components/<Name>/` with its markup and stylesheet together (`<Name>.tsx` + `<Name>.css`, imported by the component itself). New page sections should follow the same pattern: a new `src/components/<Section>/` folder composed into `App.tsx`, using the existing kebab-case BEM-ish class naming style (`hero-stage`, `hero-copy`, `mascot-frame`, etc).
- `src/components/Header/Header.tsx` owns the `navContent` JSX (nav links + dropdowns + CTA) as one fragment rendered twice: once inside `<nav className="site-nav desktop-only">`, once passed as children to `<MobileNav>`. When editing nav links/dropdowns, edit `navContent` once — both desktop and mobile pick it up.
- `src/components/NavDropdown/NavDropdown.tsx` — reusable hover/click dropdown for nav items (`label` + `items: {label, href}[]` props). On touch devices (`hover: hover` media query fails) it falls back to click-to-toggle instead of CSS hover. Used by both `Header` (desktop) and `MobileNav` (mobile), so `NavDropdown.css` has both a base ruleset and mobile-specific overrides live in `MobileNav.css` (scoped under `.mobile-nav-links`).
- `src/components/MobileNav/MobileNav.tsx` — hamburger button + slide-out panel, rendered via `createPortal` directly into `document.body` (so it isn't affected by header stacking/overflow). Toggles `document.body.style.overflow` while open to lock background scroll.
- `src/components/Cursor/Cursor.tsx` — custom animated cursor (dot + trailing ring) driven by `requestAnimationFrame`, attached via `window` pointer listeners. Self-disables when `matchMedia('(hover: hover) and (pointer: fine)')` is false (touch devices). `Cursor.css` also carries the global `* { cursor: none }` override (and per-element opt-outs) that hides the native cursor everywhere hover is supported — that's a consequence of this feature, not dead code.
- Desktop vs. mobile UI is switched with the `desktop-only` / `mobile-only` CSS classes (defined in `Header.css`), not JS breakpoint checks, except where `matchMedia` is needed to change behavior (cursor, dropdown hover support).
- `Layout.tsx` tracks pointer position on the root `<main>` via `onPointerMove`, writing `--pointer-x` / `--pointer-y` CSS custom properties onto the element for use in CSS (e.g. gradient/spotlight effects in `Layout.css`).
- `src/hooks/useInView.ts` — reusable `IntersectionObserver` hook (`{ ref, isInView }`, reveal-once, threshold configurable) for scroll-triggered entrance animations. `src/components/FolderPreview/FolderPreview.tsx` is the reference usage: it toggles an `is-visible` class from `isInView` and does all the actual animation in CSS transitions. Reuse this hook rather than writing a new observer for the next scroll-reveal section.
- `src/components/FolderPreview/FolderPreview.tsx` + `FolderShowcase.tsx` — the folder-shaped previews below the hero. `FolderShowcase.tsx` owns the data (title/description/href/photos per folder); `FolderPreview.tsx` is the presentational, data-driven single folder. The folder and its 3 photos are absolutely positioned in one shared `.folder-stage` so the photos can start tucked exactly behind the (higher z-index) folder and travel out from underneath it. Each folder's `align: 'left' | 'right'` prop sets a `--dir` CSS custom property that flips both which edge the folder anchors to and the sign of the photos' scatter transform — that's how left/right mirroring is done without duplicating the scatter math. Photos are placeholders (`{ alt }`) until a real image is wanted: add `src` to that photo's data entry in `FolderShowcase.tsx` and it renders an `<img>` instead of the placeholder box, no other changes needed.
- The photo reveal trigger branches on *input capability*, not just viewport width: `(hover: hover) and (pointer: fine)` gets the desktop hover-triggered reveal (plus the pulsing "Hover to explore" `.hover-hint` badge, hidden everywhere else); anything without real hover — phones (`max-width: 980px`) or a desktop-sized touchscreen (`min-width: 981px) and (hover: none)`) — falls back to the same `useInView`-driven scroll reveal, just with different fall directions. `prefers-reduced-motion: reduce` disables all of it by default and then explicitly re-enables the photo transition only for the hover-capable case, since that one is a deliberate user-initiated interaction rather than automatic motion.
- `<section className="folder-showcase" id="folder-showcase">` (in `FolderShowcase.tsx`) is the shared scroll target for "jump to the sections below the hero": both `src/components/ScrollCue/ScrollCue.tsx` (the bouncing bottom-center arrow, shown only while `window.scrollY < 40`, tracked via a plain `scroll` listener rather than `useInView` since it needs continuous position, not a one-shot reveal) and the hero's "Learn what CSS does" link are just plain `<a href="#folder-showcase">`s — the smooth animation is native `scroll-behavior: smooth` on `html` in `index.css`, gated under `@media (prefers-reduced-motion: no-preference)`. No JS scroll handler; a custom `requestAnimationFrame`-eased version was tried and deliberately reverted in favor of the native behavior.
- `src/components/Footer/Footer.tsx` — page footer, deliberately styled *unlike* `.site-header`: a traditional full-bleed bar in `var(--color-dark-plum)` rather than the site's usual centered rounded "card", so it reads as a distinct closing section. `Footer.css` breaks `.site-footer` out of `.site-shell`'s centered padding with the `width: 100vw; margin-left/right: calc(50% - 50vw)` full-bleed trick (safe here specifically because `.site-shell` already has `overflow-x: hidden`), then cancels `.site-shell`'s own bottom padding (`22px` desktop / `14px` mobile — must stay in sync with `Layout.css`) via a matching negative `margin-bottom` + compensating `padding-bottom`, so the dark background reaches the true edges of the page with no gap. Because the background is dark, every descendant color is overridden from the site's default dark-text-on-light to light-on-dark, and the (black-on-transparent) logo image gets `filter: brightness(0) invert(1)` to force it white — don't reuse `.brand-logo`'s styling here, the dark background needs this override. `footerColumns` in `Footer.tsx` is a small sitemap that intentionally mirrors `Header.tsx`'s `NavDropdown` data (same labels/hrefs for Events/Merch/Resources/About) — if the nav dropdowns change, update this array too, there's no shared source of truth between them. Top row is the sitemap columns (left) plus a `.footer-cta-block` (right): a `.footer-cta` "Become a Member" button + a `href="#"` "back to top" link stacked under it (native `#` anchor behavior + the global smooth-scroll from `index.css`, no JS). Bottom row is just the logo (bottom-left, no brand text) and a "Contact us!" label + mailto/Instagram/LinkedIn icon links (bottom-right) via inline SVGs (no icon asset files/libraries). The email and social URLs are real (found via web search, not guessed) but weren't confirmed by the club — verify before relying on them. On mobile the logo needs to visually reorder above everything (columns/CTA, then contact), even though it's nested inside `.footer-bottom` alongside the contact icons in the markup (kept nested so desktop's brand+contact same-row layout needs no separate markup) — the `max-width: 980px` query gives `.site-footer` a flex column and sets `.footer-bottom { display: contents; }`, which "unwraps" it so `.footer-brand` and `.footer-contact` become independently-orderable flex children of `.site-footer` right alongside `.footer-top`, each with its own `order`.

## Styling

- No CSS modules/Tailwind/styled-components — plain CSS, one stylesheet per component, imported by that component (`import './Header.css'` in `Header.tsx`, etc). `Layout.css` only holds the root `site-shell` background/grid-overlay layers. Base/reset styles and site-wide color variables are global, in `src/index.css`.
- Color palette and fonts are defined as CSS custom properties on `:root` in `src/index.css` (`--color-*` variables; fonts are Fraunces for headings, Manrope for body, loaded via Google Fonts `@import`). Reuse these variables rather than hardcoding colors.
- Responsive behavior is handled with plain `@media` queries colocated in each component's own CSS file (main breakpoint at `980px`, plus `hover`/`pointer` and `prefers-reduced-motion` queries) — there is no CSS framework.
- `src/styles/future-sections.css` holds styling for nav items that don't have a built page section yet (Events/Merch/Resources/About — things like `.join-strip`, `.mini-stats`, `.info-grid`, `.stream-list`). **This file is intentionally not imported anywhere.** When you build one of those sections, pull the relevant rules out into that new component's own CSS file rather than importing this file wholesale.

## TypeScript config notes

- `noUnusedLocals` / `noUnusedParameters` / `noFallthroughCasesInSwitch` are enabled — unused variables/params will fail `tsc -b` (and thus `npm run build`).
- `verbatimModuleSyntax` is on — type-only imports must use `import type { ... }`.
